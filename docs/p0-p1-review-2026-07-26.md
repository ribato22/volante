# Baton P0/P1 — Product and Engineering Review

Date: 2026-07-26  
Scope: product thesis, architecture, runtime correctness, routing quality, provider inventory,
safety, observability, distribution, and release readiness.

## Executive verdict

Baton addresses a real and increasingly valuable problem: users already have access to several AI
models through API keys, local endpoints, and paid agent subscriptions, but lack a transparent
control plane that selects an appropriate model for each task and explains the choice.

The original implementation had an unusually good foundation for a new project: clear supervisor /
router / projector / worker / synthesizer boundaries, canonical provider types, deterministic fake
providers, cost accounting, and extensive tests. Its main weakness was a mismatch between the
product promise and the evidence available to the router. “Best model” was mostly a tier heuristic,
the configured inventory was incomplete, several availability failures could stop a run despite a
healthy alternative, and some execution/security boundaries were too permissive for the public
positioning.

After this sprint, the P0/P1 code scope is complete for an honest alpha:

- Baton evaluates the user's explicitly configured cross-provider inventory.
- Hard capability constraints run before an explainable, deterministic score.
- Optional quality profiles can carry evaluation-derived evidence and provenance.
- Selected, rejected, fallback, and actually executed models are visible to callers.
- Worker, agentic, planning, and synthesis paths have scoped availability failover.
- Task, context, output, workspace, tool, cost, timeout, and subscription-call invariants are
  enforced at runtime boundaries.
- CLI, Web UI, MCP, MCPB, Smithery, and MCP Registry configuration surfaces are aligned.

Baton still must not claim that it empirically finds the universally best model. Today it predicts
fit from configured evidence and metadata. Automatic entitlement discovery, representative
cross-provider benchmarks, online calibration, and live health/latency signals are the P2 work that
can turn the current control plane into a defensible model-selection product.

## Meaning of “right/best model”

The current decision is:

1. Reject models that cannot satisfy the declared task type, tools, or context requirements.
2. Rank the eligible set using the selected objective:
   `quality`, `cash_protect_quota`, `local`, or `cheap`.
3. For `quality`, blend declared model metadata with an optional user-supplied
   `ModelQualityProfile`.
4. Preserve every candidate, score component, rejection reason, caveat, selected model, fallback
   event, and executed model in the route trace.

This is a sound P1 contract because it is deterministic and auditable. It becomes an evidence-based
“best for this task” claim only when the quality profiles come from representative evaluations.

## Residual release and production risks

1. **Fresh artifacts are not yet validated.** Existing `dist/` files predate this sprint and must
   not be released. A fresh isolated build was blocked because Hatchling was unavailable offline
   and the environment could not access PyPI.
2. **A new version is required.** `0.2.1` is already tagged/released. The routing contract expansion
   warrants a coordinated version decision (recommended: evaluate `0.3.0`) across Python, MCPB,
   plugin, Smithery/MCP Registry launch pins, changelog, and workflows.
3. **External integrations remain opt-in.** Real Anthropic/OpenAI-compatible calls and the Docker
   integration were not executed in the final zero-network suite.
4. **Quality is not self-calibrating.** Incorrect user metadata or stale profiles can produce a
   confident but wrong ranking; traces make this diagnosable but do not remove the risk.
5. **Availability is reactive.** Baton learns that a candidate/provider is unavailable only when a
   call fails; it does not yet maintain a health circuit breaker or latency history.
6. **Tool isolation is scoped.** The default subprocess sandbox protects against accidents, not a
   hostile program. Untrusted execution requires the documented Docker mode and a trusted daemon.
7. **URL allowlisting has residual DNS/TOCTOU limits.** The documentation should continue to avoid
   presenting it as complete SSRF protection.

## P2 priorities

1. Build a reproducible, representative cross-provider benchmark suite by task family and publish
   quality/cost/latency Pareto results.
2. Add feedback capture and automatic per-user profile calibration with sample size, recency, and
   confidence decay.
3. Discover live model entitlements where providers support it; distinguish configured, entitled,
   healthy, rate-limited, and depleted states.
4. Add provider-level circuit breakers and latency/reliability evidence so known outages do not
   repeatedly consume calls.
5. Produce a 60-second visual demo and one concrete benchmark story. Use descriptive search terms
   such as “user-owned LLM router”, “cross-provider model routing”, and “AI model control plane”
   alongside the crowded Baton name.
6. Perform the coordinated version bump, fresh wheel/sdist/MCPB build, isolated install smoke test,
   official registry validation, and only then publish.
7. Format the repository mechanically in a dedicated, reviewable housekeeping change.

## GitHub visibility assessment

The repository's first commit is dated 2026-07-20 and `v0.2.1` was released on 2026-07-24. On
2026-07-26 it is too early to interpret low attention as market rejection. Exact web searches did
not surface this repository, while several unrelated orchestration projects already use “Baton”.
The practical issue is search collision plus missing product proof, not code volume.

Do not optimize first for more installation surfaces. Optimize for one crisp promise, a visual
proof, and empirical evidence that Baton selects a better quality/cost/latency trade-off than a
single default model.
